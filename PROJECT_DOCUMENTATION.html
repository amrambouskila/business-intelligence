Overview — what this is & why

A single, reusable charting tool meant to be embedded by every future project instead of rebuilding a chart layer from scratch.

business-intelligence is a pure client-side React application. You upload a CSV/TSV, JSON, Excel, or Parquet file (or pick a built-in sample). The app parses it into a typed DataSet, analyzes every column's type and statistics, detects the overall dataset shape (e.g. single_numeric, ohlcv, hierarchy, geo_points), and then ranks the charts that actually fit that data. You pick one, the app auto-assigns columns to chart roles, and renders it — in dark or light theme, with per-chart option controls, filters, annotations, layer compositing, and image/data export.

The motivation, stated in the master plan: every project the owner builds eventually needs charts, and reaching for a new library each time (Chart.js here, Plotly there, hand-rolled d3 elsewhere) means re-solving file upload, shape detection, chart selection, theming, and large-data performance over and over. This project centralizes that work once, with a deliberately WebGL-capable stack, so the cost is paid a single time.

The product's defining feature is the shape → ranked-suggestion flow: the user never has to know which chart to pick. The data tells the app what's possible, and the registry returns the compatible charts sorted by fit (most specialized first). The architecture is a chart registry populated by side-effect imports — every chart type is one self-contained file that calls chartRegistry.register(...), so adding the 194th chart is purely additive and touches nothing else.

Key concept
There is no backend in this phase. Everything runs in the browser: parsing, shape detection, suggestion, rendering, export. A FastAPI/Postgres/DuckDB backend is planned for Phase 4 only when datasets exceed browser memory. Do not introduce a server here.

Architecture

A linear data pipeline feeds a registry-driven rendering layer; Zustand stores hold all app state; React components are the glue.

There are four conceptual subsystems, each with a clear boundary:

Data pipeline→Chart registry→Renderer backend→Canvas mount

State (5 Zustand stores) and UI components wrap around this. The contracts that cross every boundary — DataSet, DataView, ChartDefinition, ChartConfig, ThemeTokens — are defined once in src/types/data.ts and src/charts/types.ts and never duplicated locally.

Module dependency graph

Boot sequence

The app entry is src/main.tsx, which mounts src/app/App.tsx. Chart registration is the critical timing concern: the three core families (distribution, time-series, relationships) register eagerly as a side effect of importing the families barrel, while the other ten families are lazy-loaded. App.tsx awaits ensureAllFamiliesLoaded() and shows a "Loading chart library…" state until all 193 are registered — so the registry-reading panels (picker, suggester) never see a partial catalog.

Key concept — one canvas per renderer
Renderers never share a canvas. ChartArea.tsx keys the render root on chartType, so switching charts unmounts the old renderer and fires cleanup. This is load-bearing for WebGL backends: deck.gl's DeckGLChart calls deck.finalize() on unmount, and regl/Canvas2D wrappers destroy their contexts — without this, switching charts leaks WebGL contexts, buffers, and textures.

Core modules & components

The heart of the doc — each major subsystem with its real logic and the exact files to read or edit.

Chart registry src/charts/registry.ts

A singleton class holding three indexes: by type (the canonical map), by family, and by data shape. register() throws if a type is registered twice — so every chart file must register exactly once, and duplicate registration is caught loudly. The registry is populated entirely by side-effect imports; no central list of charts exists.

src/charts/registry.tsThe singleton + its three indexes and accessors.
src/charts/families/index.tsEager core families + lazy ensureAllFamiliesLoaded() barrel.
Renderer architecture (4 backends) src/charts/renderers/

Every chart's createRenderer() returns an object implementing the ChartRenderer interface: render(data, config, theme) → ReactElement plus an optional destroy?(). Four abstract base classes implement that interface and own the cross-cutting concerns so each chart only supplies its specifics:

EChartsBaseRenderer
Subclasses override buildOption(). The base applies the empty-data guard (isEmpty/emptyMessage hooks), the theme defaults (transparent background, foreground text color, font), and — when window.__E2E__ is set — disables ECharts animation so visual baselines are deterministic.
DeckGLBaseRenderer
Subclasses override buildLayers() and optionally getViewKind() (map/orbit/orthographic) + getInitialViewState(). Renders into DeckGLChart, which calls deck.finalize() on unmount.
Canvas2DBaseRenderer
Subclasses draw directly to a 2D context. Canvas2DChart owns the canvas with device-pixel-ratio scaling, resize redraw, missing-context safety, and cleanup. gauge is the proof chart.
ReglBaseRenderer
Custom WebGL shaders. ReglChart owns the canvas + regl instance with DPR sizing, resize redraw, and regl destruction on unmount. image_raster_plot is the proof chart.
echarts-renderer.tsxEChartsBaseRenderer abstract class.
deckgl-renderer.tsxDeckGLBaseRenderer with view selection.
DeckGLChart.tsxFC wrapping <DeckGL>; finalize() on unmount.
canvas2d-renderer.tsxCanvas2DBaseRenderer abstract class.
Canvas2DChart.tsxDPR-scaled canvas wrapper + cleanup.
regl-renderer.tsxReglBaseRenderer abstract class.
ReglChart.tsxregl canvas wrapper + context destruction.
EmptyChartState.tsxThemed empty-state placeholder shown by the guard.
An individual chart file src/charts/families/distribution/histogram.ts

The template every chart follows: declare option specs, define a renderer subclass overriding buildOption() (or buildLayers()), and call chartRegistry.register({...}) at module scope with the full ChartDefinition — type, family, name, renderer backend, compatibleShapes, requiredColumns (role + accepted types), optional options, and a createRenderer() factory. The histogram pulls its numeric column, filters non-finite values for the empty guard, bins via the shared histogramBins helper, and themes its bar via categoricalColor.

A deck.gl geographic chart follows the same shape but extends DeckGLBaseRenderer and overrides buildLayers() + getInitialViewState() instead — see point_map.ts, which extracts finite lat/lon points, builds a ScatterplotLayer, and derives a bounds-centered MapView state.

histogram.tsCanonical ECharts chart example.
point_map.tsCanonical deck.gl chart example.
gauge.tsCanvas2D chart example.
image_raster_plot.tsregl chart example.
Data loader & parsers src/data/loader.ts

loadFile(file) dispatches by extension to the right parser, then runs a uniform post-pipeline: normalize formatted values → analyze columns → detect shape → build columnar index → assemble a DataSet with a fresh UUID. Adding a format means adding a parser + one branch here.

Column analysis & shape detection src/data/shape-detector.ts

analyzeColumns() infers each column's type, null/unique counts, numeric stats (min/max/mean/median/std/q25/q75), top categorical values, and date ranges. inferType() is order-sensitive: geo coordinate names (lat/lng/...) take precedence over plain numeric, then boolean, numeric (int vs float), datetime (by name heuristic then string parsing), and finally category-vs-text by unique ratio. detectShape() then maps the column profile to one of 18 DataShape values via a priority ladder: OHLCV and named matrix first, then geo, survival, hierarchy, network, intervals, event logs, time-series variants, and numeric-count fallbacks.

shape-detector.tsanalyzeColumns + inferType + computeStats + detectShape (named thresholds, no magic numbers).
Chart suggester (the differentiator) src/data/chart-suggester.ts

The "which chart?" answer. suggestCharts(shape, columns) scores every registered chart and returns the applicable ones, best first. A chart scores 0 (excluded) unless its compatibleShapes includes the detected shape and every required role can be filled by a distinct column (the isFillable consume-on-assign check mirrors ChartArea's auto-assignment). Among applicable charts, more specialized ones (fewer compatible shapes) score higher; ties break by name.

chart-suggester.tsscoreChart + suggestCharts + isFillable.
Filters & transforms src/data/transforms.ts

applyFilters(ds, filters) turns a DataSet + active Filter[] into a DataView (filtered rows + recomputed columnar index). With no active filters it returns the dataset's arrays directly (zero-copy fast path). matchFilter supports eq/neq/gt/gte/lt/lte/in/between/regex; invalid regex fails closed (returns no match) rather than throwing during render. Group-by aggregation for categorical charts lives separately in groupByAggregate.ts.

transforms.tsapplyFilters + matchFilter.
groupByAggregate.tssum/mean/count/min/max/median group-by for bar/pie/lollipop/etc.
Reference-validated stats layer src/data/stats/

Charts that need real math share a tested compute layer rather than re-implementing statistics. Each module is validated against documented reference values (no mocking of the math). Examples: quantiles (type-7 percentiles), kernelDensity (gaussian KDE, Silverman sample-sd bandwidth), buildHierarchy (flat id/parent → tree, with cycle-breaking to avoid infinite ECharts trees), rocCurve/prCurve (tie-stable AUC/AP), calibrationCurve, normalQuantile (Acklam probit) + qqPoints, autocorrelation/partialAutocorrelation, and survivalCurve (Kaplan-Meier).

src/data/stats/All shared statistical compute, one concept per file.
src/charts/echarts/Shared ECharts option helpers: pivotLongForm, histogramBins, matrixGrid, relationshipGrid, multivariate, axis/grid/tooltip.
ChartArea — orchestrator & auto-assignment src/components/chart-area/ChartArea.tsx

The center of the UI. It reads the active dataset, layer stack, and filters; computes the filtered DataView (memoized); and for each layer fills any unassigned required role with a distinct column, preferring a column whose name matches the role (with aliases like timestamp→date, event→label). If a required role can't be filled it shows "No compatible column for: …". It renders the active layer plus any other visible, fully-filled layers into the same render root for basic compositing — each via ChartCanvas, which memoizes the renderer per chartType so unmount/cleanup only fires on a real chart switch. The header exposes per-role column pickers, optional-role pickers, and PNG/SVG export buttons. The render root carries data-* hooks (data-chart-active, data-chart-unfilled, etc.) that drive the Playwright gate.

ChartArea.tsxAuto-assignment, filtering, layer compositing, export header, e2e hooks.
ChartCanvas.tsxPer-chartType renderer dispatch + memoization (cleanup boundary).
ColumnPicker.tsxThe role→column <select> in the chart header.
Sidebar & tabs src/components/sidebar/

Each tab is its own file: DataTab (dataset switcher, row preview, filter authoring with live row-count, annotations, CSV + chart-spec export), ChartPicker (the ranked "Suggested for <shape>" surface with a "Show all charts" escape hatch into family browsing), LayersTab (layer activation/removal, visibility, y1/y2 axis), and ChartOptionsPanel (generic option controls driven by each chart's options spec).

How to run it

Local dev with Vite, or the full Docker/nginx production path via the launcher.

Local development

  1. Install dependencies on the target OS: npm ci (required — node_modules is gitignored and non-portable across OS/arch).
  2. Start the dev server: npm run dev → opens on http://localhost:5176 with hot reload.
  3. Click Samples and pick a dataset (or Upload a CSV/JSON/Excel/Parquet file) to see shape detection + suggestions immediately.

Docker (production-equivalent)

  1. (Optional) copy .env.example to .env and set BI_PORT.
  2. Run bi_service.sh (macOS/Linux) or bi_service.bat (Windows). It runs docker compose up --build -d and prints the service URL.
  3. Open http://localhost:5176 (or your BI_PORT).
  4. At the prompt choose: [k] stop (keep image) · [q] stop + remove image · [v] also remove volumes · [r] full restart (rebuild + relaunch).
Watch out — non-TTY launchers
The launcher's [k]/[q]/[v]/[r] loop reads from stdin. Running bi_service.bat via a non-interactive runner (e.g. PyCharm right-click → Run) will hang at the prompt — run it from a real terminal, or pipe a choice ('k' | cmd /c bi_service.bat) as the status doc's verification did.

How to edit / extend it

Practical, owner-focused recipes. The whole architecture is designed so the common change — adding a chart — touches one new file plus one barrel line.

Add a new chart type
  1. Read the chart's spec in CHARTS.md (family, minimum columns, intended renderer backend).
  2. Create src/charts/families/<family>/<chart_name>.ts (snake_case, matching the catalog name).
  3. Extend the correct base renderer (EChartsBaseRenderer → override buildOption(); DeckGLBaseRenderer → override buildLayers() + view hooks; or Canvas2D/regl bases).
  4. Call chartRegistry.register({...}) at module scope with the full ChartDefinition — type, family, renderer, compatibleShapes (aligned with the shape detector), requiredColumns (role + acceptedTypes), optional options, createRenderer.
  5. Add a side-effect import to the family's index.ts barrel (otherwise it never registers).
  6. Add a unit test at tests/unit/charts/families/<chart_name>.test.ts exercising buildOption/buildLayers output + the empty-state path.
  7. Add the chart→sample mapping in tests/e2e/chart-samples.ts, then generate a Gate-3 baseline with ./run_e2e.sh update (or run_e2e.bat update) in the pinned Docker image.
  8. Reuse the shared helpers (src/charts/echarts/, src/data/stats/) rather than re-implementing axes/pivots/statistics.
Tip — use the scaffolders
The new-chart command and scaffold-charts skill generate the boilerplate. The registry contract test (registry-contract.test.ts) validates that your chart's declared backend matches a live base class, and the e2e drift guard (e2e-coverage.test.ts) fails if it lacks a visual-gate entry.
Add a new data format
  1. Create a parser in src/data/parsers/ returning { rows, columnNames }.
  2. Add an extension branch in src/data/loader.ts's dispatch.
  3. Accept the extension in the upload input's accept= list in Toolbar.tsx (a test guards against forgetting this).
  4. Add tests at tests/unit/data/parsers/<format>-parser.test.ts + loader routing coverage.
Add a new chart family
  1. Create src/charts/families/<family>/ with an index.ts barrel.
  2. Import the new barrel in src/charts/families/index.ts (eager or lazy list).
  3. Add the family key to the ChartFamily union and FAMILY_META (label + icon) in src/charts/types.ts.
Add a new detected shape, or change suggestions

Add the variant to the DataShape union in src/types/data.ts, then add detection logic to detectShape() in shape-detector.ts (respect the priority ladder — more specific shapes first). Charts surface for the shape automatically once they list it in compatibleShapes. Ranking heuristics live in chart-suggester.ts.

Watch out
Aggressive name-matching in shape detection can degrade real suggestions (e.g. forcing a time+event time series into survival and emptying the suggestion list). New detection rules need a negative test proving they don't mis-fire on ordinary data.
Change theming / colors

Edit the token sets in tokens.ts (chart colors) and the CSS custom properties in src/index.css (UI chrome). Charts must read colors from theme.colorScale/sequentialScale/etc. via helpers like categoricalColor — never hard-code a hex outside the token files (a self-audit rule, enforced by source grep).

Add a per-chart option control

Add a ChartOptionSpec entry to the chart's optionSpecs and reference it in the options field of its ChartDefinition. The generic ChartOptionsPanel renders it automatically (number/toggle/select/color), and resolveOptions applies the default + validates the value in the renderer. No per-chart UI branching is needed.

Testing

Two complementary layers: Vitest unit/component tests at 100% coverage, and a Playwright visual-regression gate that renders every chart in a real browser.

Unit / component (Vitest)

~1463 tests under tests/unit/, mirroring src/ structure. The setup file (tests/setup.ts) imports jest-dom, calls cleanup() in afterEach (Vitest does not auto-clean like Jest), and mocks ResizeObserver/canvas/WebGL since jsdom has none. Coverage is gated at 100% (statements/branches/functions/lines) in vitest.config.ts, with main.tsx, App.tsx, type-only files, barrel index.ts files, and CSS excluded. A handful of genuinely-unreachable defensive branches use /* v8 ignore */ with justifying comments.

Visual regression (Playwright — "Gate 3")

jsdom mocks canvas/WebGL, so unit tests cannot prove a chart actually paints. The Playwright suite (tests/e2e/charts.spec.ts) drives the real UI for all 193 charts: load the chart's deterministic sample → "Show all charts" → click the chart → wait for auto-assign → assert both a non-blank canvas (reads pixels) and a screenshot baseline. Baselines live in tests/e2e/__screenshots__/ (192 PNGs; force_directed_graph is floor-only because its layout is Math.random()-seeded). The chart→sample map is chart-samples.ts. Runs only in the pinned mcr.microsoft.com/playwright:v1.60.0-noble image so baselines are deterministic.

Determinism is engineered, not lucky
Sample data is generated from a fixed-seed mulberry32 PRNG (sample-data.ts), and the ECharts renderer disables its animation when window.__E2E__ is set — so screenshots capture a stable final frame. A vitest drift guard (e2e-coverage.test.ts) fails if any registered chart lacks a visual-gate entry, and a deck.gl switch-stress spec (deckgl-switch-stress.spec.ts) exercises repeated real-GL chart changes to catch cleanup leaks.

Build, CI & deployment

GitHub Actions pipeline gated on a 100% coverage floor and a 193-chart visual gate, deploying via a multi-stage Docker image to nginx.

The pipeline in .github/workflows/ci.yml runs on push/PR to main, dev, staging. lint gates everything; typecheck and test both depend on it; build and the Playwright e2e visual job both depend on typecheck+test; docker runs only on main/staging. The visual job runs in the pinned Playwright container so committed baselines render identically. Coverage drop fails the test stage.

Docker image

Two-stage build in Dockerfile: stage 1 (node:20-alpine) runs npm ci + npm run build; stage 2 (nginx:alpine) copies dist/ and the SPA nginx.conf (try_files fallback to index.html, immutable asset caching, no-cache index.html). docker-compose.yml is a single service publishing ${BI_PORT:-5176}:80 with restart: unless-stopped — correctly minimal since there's no database or second service.

Releases / versioning

Strict semver. The version field in package.json is the single source of truth and is bumped only by the release pipeline (.github/workflows/release.yml) — never edited by hand. Changelog entries land in docs/versions.md under the computed next version, one unreleased version at a time.

Domain glossary

Terms that recur across the code and docs.

Chart family
One of 13 categories charts are grouped into (distribution, categorical, time-series, …). Defined by the ChartFamily union + FAMILY_META.
DataShape
An 18-value enum describing the overall structure of a dataset (e.g. ohlcv, hierarchy, geo_points). Detected from column metadata; drives which charts are suggested.
ColumnRole
A named slot a chart needs filled (e.g. value, x, lat) with its accepted column types. Auto-assigned from columns in ChartArea.
Renderer backend
Which engine draws a chart: echarts, deckgl, regl, or canvas2d. Each chart picks exactly one; canvases are never shared.
Registry / side-effect import
The chartRegistry singleton is populated by importing each chart file for the register() call it runs at module scope — there is no central chart list.
Layer
One chart instance in the stack (LayerConfig): a chart type + its column assignments + options + axis + visibility. Multiple visible layers can composite into one render root.
DataView
A filtered/transformed snapshot of a DataSet handed to renderers; carries the filters that produced it.
Suggestion / fillability
A chart is suggested for a dataset only if its shape matches and every required role can be filled by a distinct column (consume-on-assign).
OHLCV
Open/High/Low/Close/Volume — the financial time-series shape that drives candlestick/OHLC/price-volume charts.
Gate 3
The Playwright visual-regression harness that renders all 193 charts in a real browser and asserts non-blank canvas + screenshot baseline.
